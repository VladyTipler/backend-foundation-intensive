# Лаборатория: готовая подготовка каждого дня

Все программы подготовки уже находятся в репозитории. Не нужно копировать из Notion код сидеров, создавать вспомогательные файлы или вручную сочинять сотни записей.

## Как открыть

**Windows:** открой `lab.cmd` двойным щелчком в папке проекта.
**macOS:** открой `lab.command` (или запусти из Terminal). **Linux:** `./lab.sh`.
Одинаковый для всех систем вариант из корня проекта: **`npm run lab`**.

Нужны установленные Node.js 24 и Docker Desktop из Дня 0. Само меню использует встроенные средства Node и запускается даже до установки npm-зависимостей.

В меню сначала выбери **0** — создастся отсутствующий `.env`, выполнятся проверки. **I** установит зависимости backend и готового frontend по lock-файлам. **U** запустит PostgreSQL, Redis и Adminer. Перед действием меню спросит подтверждение. Существующие `.env` и отчёты не перезаписываются.

Обычный backend и frontend работают в своих терминалах, как описано в Дне 0. Помощник не запускает вместо ученика готовую реализацию API. Выбирай номер дня, подтверждай и читай результат. В дальнейшем не требуется вспоминать разные команды подготовки.

## Что готовится

| Пункт | Готовый материал | Что сначала делает ученик |
|---|---|---|
| **0** | Настройки при их отсутствии, папки, диагностика программ и БД; I/U для установки и старта | Устанавливает Node/Docker, открывает меню |
| **1** | 100 пользователей, 1000 вакансий и 300 откликов на пустой совместимой БД; минимум 12 откликов у двух вакансий для HAVING | Создаёт свои users/jobs/applications, FK, UNIQUE, CHECK |
| **2** | Переиспользование набора дня 1, CSV около 20 МБ для streams; пункт N добавляет отдельные 20 авторов и 100 вакансий | Пишет Node/ORM, миграции и API; helper этого не реализует |
| **3** | Два учебных аккаунта через настоящий register/login/CSRF ученика; 30 личных откликов каждому, свои вакансии | Пишет регистрацию, password hashing, сессии и CSRF; добавляет nullable password_hash по уроку |
| **4** | До 250 подготовленных личных откликов на аккаунт, поля для проверки CSV; пункт E заказывает 3 настоящих экспорта | Реализует exports, очередь и worker; helper не подставляет completed |
| **5** | Те же данные и аккаунты, проверка наличия файлов; пункт M создаёт отдельную пустую БД для миграций | Создаёт Dockerfile, сервисы API/worker, свои миграции |
| **6** | Аккаунты A/B, чужие записи, текст с кавычками/HTML-подобными символами и формулоподобное поле; T отправляет 20 GET, E — задания | Добавляет метрики/логи/проверки доступа; данные не равны готовому мониторингу |
| **7** | Сохранённая история для финальной проверки, тот же набор A/B и отчёт | Проверяет весь путь и отказы, защищает решения |
| **8** | Те же данные и проверка аккаунтов через выбранный новый API | Переносит backend на Nest, указывает LAB_API_URL нового API |

Числа — размер исходного набора, **не требование, что в общей БД всегда ровно столько строк**. Помощник добавляет недостающие данные. Уже существующие строки, дополнительные сценарии и собственная практика остаются. В конце выводятся фактические числа и ID примеров: не предполагай, что первая вакансия обязательно имеет ID=1.

### Индексы: пункт X

Пункт X добавляет **100000** вакансий, не удаляя обычный набор и аккаунты. Среди новых строк ровно 1% с `company = 'Lab Rare Index Co'`, 80% с `company = 'Lab Common Index Co'`. Проверяй фактическую долю во всей таблице.

Сидер обновляет статистику `ANALYZE`, но **не создаёт и не удаляет индексы**. Два сравниваемых запроса теперь фильтруют указанные компании, а не Google из старого разрушающего сидера. Для планов используй свои запросы `EXPLAIN (ANALYZE, BUFFERS)` до/после самостоятельно созданного индекса. Повтор X не создаёт ещё 100000 одинаковых строк.

### N+1: пункт N

Вакансии имеют заголовки `[LAB nplusone ...]`, авторы — адреса `nplus-author-...@example.test`. ID присваивает PostgreSQL, helper их печатает. Наивную загрузку и её исправление пишет ученик. Наличие 100 вакансий само по себе не создаёт N+1.

### Аккаунты: почему подготовка дня 3 требует написанный auth

Нельзя заранее записать произвольный hash и обещать совместимость с любой реализацией проверки пароля. Поэтому помощник вызывает **твой** `/auth/csrf`, `/auth/register`, `/auth/login`, `/auth/me`. Hash вычисляет твой backend. Cookie и CSRF сохраняются в отдельном временном клиенте; защита не обходится.

Если маршрута ещё нет, помощник точно сообщает, какой шаг сначала реализовать. Повтори тот же пункт после реализации. Он не выдаст чужое готовое решение, фиктивного пользователя или зелёную отметку прохождения.

Случайные учебные пароли сохраняются в `var/lab/<локальный-профиль>/accounts.private.json`, не в Git. **C** показывает их на твоём экране; не используй этот пункт на публичной демонстрации. Для входа через UI скопируй только свои учебные email/пароль. Это не рабочие доступы. Помощник никогда не меняет пароль существующего аккаунта.

В `.env` при нестандартных портах задай `LAB_API_URL` (адрес Node/Nest, без `/api`) и `LAB_ORIGIN` (адрес браузерного клиента). Например, для Nest: `LAB_API_URL=http://127.0.0.1:3002`. Настройка `API_PROXY_TARGET` в `web/.env.local` — отдельная настройка Vite. Они должны указывать на одну реализацию.

### Реальные экспорты и запросы

**E** делает до трёх `POST /exports` через твой API с сессией, CSRF и сохранёнными Idempotency-Key. Повтор E использует те же ключи. При timeout он не предполагает, что запись отсутствует. ID выводятся для открытия в UI. Новые независимые экспорты создавай кнопкой интерфейса.

Помощник не заполняет таблицу exports строками «completed», не пишет CSV за worker и не создаёт метрики в обход приложения. **T** делает 20 ограниченных последовательных запросов чтения `/jobs`, чтобы твои собственные метрики получили настоящие наблюдения. Это не нагрузочный тест production.

### Проверка миграций: пункт M

M создаёт только **пустую** БД `job_tracker_lab_migrations` на том же локальном сервере. Если БД уже существует — сохраняет её. Основной DATABASE_URL не меняется, таблицы не копируются, твои миграции не выполняются. Выбор этой БД и запуск своей истории — практика Дня 5.

## Как сохраняется работа ученика

Подготовка не использует DROP, DELETE, TRUNCATE или UPDATE бизнес-данных. Вставки проходят в одной транзакции на одном подключении. Набор не очищает сессии Redis и не меняет ограничения БД.

Локальный журнал `fixtures-v1.json` запоминает реальные ID подготовленных строк. Повторный запуск не перезаписывает отредактированные названия/статусы и не восстанавливает намеренно удалённые строки. Не удаляй `var/lab` между днями: это часть состояния лаборатории, как локальные данные БД. При переносе одной и той же учебной БД на другой компьютер перенеси и этот приватный журнал безопасным способом, не через публичный Git.

На чистой БД подготовка воспроизводима при закреплённой версии Faker: фиксированы seed и опорная дата. При ручном сбросе таблиц с повторным использованием старых ID не используй старый журнал как доказательство соответствия. Для независимого прохождения создай новую учебную БД с именем `job_tracker_lab_*`. Помощник не угадывает, какие ручные изменения означают «восстановить всё».

Защита допускает только loopback-адреса и учебные имена БД, запрещает NODE_ENV=production и перенаправления HTTP. Это дополнительная страховка, **не разрешение использовать рабочую БД под учебным именем**.

`seed:base`, `seed:day1:indexes`, `seed:scenario:n-plus-one` сохранены как совместимые входы в новый безопасный помощник. Старое поведение «сначала очистить всё» больше не используется. Отдельные `db:clean`/`db:reset` остаются разрушительными ручными инструментами: меню их не вызывает.

## Что считаем результатом

«Данные готовы» ≠ «урок выполнен». Помощник проверяет минимум совместимости структуры, но не доказывает все FK, правильность запросов, индексов, ownership, retry или метрик. Это проверяет ученик по практическому заданию. В каждый день создаётся только отсутствующий шаблон `docs/day-N-results.md` — без выдуманных результатов.

## Для преподавателя: проверка помощника

`npm run lab:test` запускает отдельные тесты учебной подготовки; они не являются тестами backend ученика.

Интеграционный тест требует **одноразовую** `job_tracker_lab_test`, `LAB_TEST_DATABASE_URL` и явный `LAB_ALLOW_TEST_RESET=YES`. Только он имеет право пересоздавать её тестовую схему из `tests/lab/fixture.sql`. Fixture не применяется ни при старте, ни при подготовке дней. Без этих настроек реальный PostgreSQL-тест пропускается, что видно в отчёте.

Официальные источники: [воспроизводимость Faker](https://fakerjs.dev/guide/usage#reproducible-results), [транзакции node-postgres](https://node-postgres.com/features/transactions), [встроенное меню readline](https://nodejs.org/api/readline.html).
