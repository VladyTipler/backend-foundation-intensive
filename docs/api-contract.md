# API-контракт Job Tracker Lab

Это договор между готовым `web/` и backend ученика, **не реализация заданий**. Версия контракта: 1.

## Как читать договор

Адреса ниже относятся к Node API (по умолчанию `http://127.0.0.1:3000`).
Браузер вызывает `/api/jobs` на Vite; Vite удаляет `/api` и передаёт `/jobs` в Node.
Не добавляй второй префикс `/api` на backend, если не менял настройку прокси.

`web/src/contracts.ts` проверяет ответы в runtime: HTTP 200 с неправильным JSON отображается как ошибка контракта, не как успешный пустой список.
Даты: ISO 8601. Идентификаторы: положительные целые в строке (`"42"`); безопасные JSON-числа тоже принимаются. BIGINT не преобразовывай в JS Number с потерей точности.

Это **формат API**, а не обязательная форма хранения. В БД можно нормализовать компании, хранить `company_id`, использовать `created_at` и любые ORM-имена. Backend собирает DTO (объект ответа) с полями `company`, `createdAt`, например через JOIN. Пользовательский интерфейс не диктует структуру твоих таблиц.

## Этапы клиента

| День | Что включено | Что реализовать |
|---|---|---|
| 0–1 | Обзор и проверка /health | Уже есть в starter; SQL выполняешь отдельно |
| 2 | Вакансии, поиск, страницы, создание/редактирование/удаление | /jobs |
| 3 | Аккаунт и отклики; записи с сессией и CSRF | /auth/*, /applications |
| 4–7 | Экспорт и проверка статуса | /exports |

Выбор дня — только удобство навигации, **не защита API**. Любой пользователь может изменить его или отправить запрос напрямую. Все проверки доступа выполняет сервер независимо от выбранного дня.
В Дне 2 допускается локальный учебный CRUD без auth. Автор определяется сервером из учебных данных, не из произвольного userId клиента. После Дня 3 все изменения защищены сессией и проверкой владельца.

## 1. Проверка окружения

`GET /health` → 200:
```json
{"status":"ok","databaseTime":"2026-09-19T00:00:00.000Z"}
```

## 2. Вакансии

`GET /jobs?page=1&limit=10&q=Backend&company=Acme&sort=created_at_desc` → 200:
```json
{"items":[{"id":"42","title":"Backend Developer","company":"Acme","createdAt":"2026-09-01T10:00:00.000Z"}],"total":1,"page":1,"limit":10}
```
`q` и `company` необязательны. `q` — регистронезависимое вхождение в название; `company` — точное совпадение. `sort` — `created_at_desc` или `created_at_asc`, при равных датах добавляй сортировку по id в том же направлении.
`total` — число ВСЕХ подходящих строк до LIMIT, а не размер текущей страницы. `page` начинается с 1; для клиента limit=10. Пустой результат: `items: []`, `total: 0`.
`createdAt` можно не отправлять в раннем упражнении; остальные поля вакансии обязательны.

`POST /jobs`, JSON:
```json
{"title":"Backend Developer","company":"Acme"}
```
Успех → 201 с `{"job":{"id":"42","title":"Backend Developer","company":"Acme"}}`.

`PATCH /jobs/42` получает те же поля; успех → 200 с объектом `job`.
`DELETE /jobs/42` → **204 без тела**. Сервер определяет, что делать с зависимыми откликами; при запрете удаления возвращает 409 и не теряет данные.
День 3+: запрет чужого изменения проверяет backend. Кнопки могут быть видимы — это позволяет проверить ответ 403. Для скрытия кнопок можно позже расширить DTO полем canEdit, но оно не заменяет серверную проверку.

## 3. Сессия и CSRF — выбранный путь клиента

Для основного UI используем **server-side session + HttpOnly cookie**. JWT остаётся альтернативным учебным заданием, но автоматического переключения между двумя механизмами здесь нет.
`GET /auth/csrf` → 200 `{"csrfToken":"непредсказуемый_токен"}`. Доступен до входа; токен связан с текущей (в том числе анонимной) сессией. Ответы auth: `Cache-Control: no-store`.
Перед каждым изменяющим запросом с Дня 3 клиент получает свежий токен и отправляет его в `X-CSRF-Token`. Backend проверяет токен И разрешённый Origin, а не просто наличие заголовка. Это относится и к login/register/logout.
В локальном HTTP cookie не ставится `Secure`; в production HTTPS флаг обязателен. Используй `HttpOnly; SameSite=Lax; Path=/`, без Domain для localhost. После входа ротируй ID сессии. Не изобретай криптографию самостоятельно — используй библиотеку сессий/CSRF.

`POST /auth/register`: `{ "name": "Анна", "email": "anna@example.test", "password": "учебный-пароль" }`.
`POST /auth/login`: `{ "email": "anna@example.test", "password": "учебный-пароль" }`.
Успех: 201 для регистрации или 200 для входа; обе операции устанавливают сессию и возвращают:
```json
{"user":{"id":"101","name":"Анна","email":"anna@example.test"}}
```
`GET /auth/me`: 200 с тем же объектом `user` либо 401 без валидной сессии.
`POST /auth/logout`: отозвать сессию, очистить cookie и вернуть 204.
Ошибка login: 401 с нейтральным сообщением. Ограничь частоту попыток на сервере.

У пользователей базового seeder **нет паролей**. После миграции auth разреши им существовать без password_hash или подготовь отдельный auth-seeder; для UI зарегистрируй отдельного пользователя. Не придумывай ему готовые данные для входа.
Никогда не запускай seeder повторно на БД с нужными откликами, не посмотрев, что он очищает.

## 4. Отклики текущего пользователя

`GET /applications?page=1&limit=10&status=interview` → 200:
```json
{"items":[{"id":"7","job":{"id":"42","title":"Backend Developer","company":"Acme"},"status":"interview","createdAt":"2026-09-02T10:00:00.000Z"}],"total":1,"page":1,"limit":10}
```
Допустимые статусы: `new`, `screening`, `interview`, `offer`, `rejected`. Фильтр status необязателен. Сервер фильтрует по владельцу из сессии, затем применяет фильтр и пагинацию.
`POST /applications`: `{ "jobId": "42" }` → 201 `{"application":{...}}`. Внутри application та же структура, что в списке. Повтор пары user/job → 409, защищённый ограничением UNIQUE, не только проверкой в коде.
`PATCH /applications/7`: `{ "status": "interview" }` → 200 `{"application":{...}}`.
`DELETE /applications/7` → 204. Чужой объект: 403 или намеренно 404 без раскрытия чужих данных.
Клиент не отправляет userId в body. Прямые HTTP-запросы с подставленным userId должны быть так же безопасны.

## 5. Экспорт через очередь

`POST /exports` с JSON `{ "format": "csv" }`, сессией, `X-CSRF-Token` и `Idempotency-Key` → **202**:
```json
{"export":{"id":"42","status":"queued"}}
```
Ключ имеет область пользователя и операции. Тот же ключ + то же тело возвращает тот же export; другое тело с тем же ключом → 409. Резервирование ключа и создание export должны выдерживать одновременные запросы; проверка «сначала SELECT, потом INSERT» сама по себе недостаточна.
ID export — ID бизнес-записи в БД, не обязательный формат BullMQ job.id. Очередь и публикацию задания реализует ученик.
`GET /exports/42` → 200:
```json
{"export":{"id":"42","status":"processing","progress":25}}
```
Статусы: `queued`, `processing`, `completed`, `failed`. progress — необязательное число 0–100. Не отправляй выдуманный прогресс: без него интерфейс покажет неопределённое ожидание.
UI опрашивает статус через 2 секунды после предыдущего ответа, без перекрытия запросов. При завершении, ошибке, уходе со страницы или после 5 минут опрос прекращается; можно продолжить по ID. Остановка опроса не отменяет задачу.
`GET /exports/42/file`: при готовности → 200, `Content-Type: text/csv; charset=utf-8`, тело — CSV. Желателен `Content-Disposition: attachment; filename="applications-42.csv"`. До готовности → 409; чужой файл → 403/404.
CSV возвращает сам API с проверкой сессии/владельца. Не требуется настраивать S3; это отдельное расширение упражнения. Если экспорт открывают в Excel, защити текстовые ячейки от formula injection.

## 6. Ошибки и диагностика

Один возможный формат ошибки:
```json
{"error":{"code":"VALIDATION_ERROR","message":"Проверь название вакансии"},"requestId":"req-123"}
```
Отдавай подходящий HTTP status, не 200 с полем error. Не возвращай пароли, токены, SQL connection strings или stack trace. Добавляй `X-Request-Id` для связи с серверными логами.
Клиент не повторяет изменяющие запросы автоматически. HTTP timeout НЕ доказывает, что сервер не выполнил запись: перед повтором надо проверить состояние; для экспорта повторяется тот же idempotency key.
В инспекторе хранится до 30 ответов в памяти вкладки. Auth-body полностью скрыт; известные secret-поля маскируются, вложенность и длина ограничены. Это не универсальный сканер секретов: backend всё равно не должен возвращать чувствительные данные. Используй только учебные аккаунты.
